# FChart銘柄・企業データ結合規則解明 作業報告書

対応する正式作業指示書：`作業指示/20260922-0124_FAND_FChart銘柄企業データ結合規則解明_作業指示書.md`

## 結論

現行 `Userkabu.ini` 第4列（1始まり）から、`kigyo.dat`、`kigyo2.dat`、`kigyo3.dat` の共通**候補レコード座標**を、4,240銘柄について一意かつ再現可能に算出できることを確認した。これは企業同一性又は第4列の業務意味を確認したものではない。

ただし、この候補座標規則だけでは企業同一性の意味付け、49銘柄の例外、または `Zaimu.dat` の財務レコードまでを保証できない。下記の追加調査台帳でも、この不足を推測せず補える直接証拠は確認できなかった。よって完了条件B（現有資産だけでは全銘柄・企業・財務を一意に結合する規則は確定不能）に到達した。企業業績・財務DBの正式実装は開始しない。

## 調査範囲

- 読取り専用で `C:\fchart\kabu.lst`、`Userkabu.ini`、`gyoseki\kigyo.dat`、`kigyo2.dat`、`kigyo3.dat`、`Zaimu.dat` を解析した。
- 既存の35件教師データ、旧版比較及びFChartのデータリンク設計に関する既存調査成果物を照合した。
- DB、Data Gateway、Console、正式コード、設定及びFChart原本は変更していない。

## 確認済み事実

| 観点 | 結果 |
| --- | --- |
| 銘柄マスター | `kabu.lst` と `Userkabu.ini` は4,289行で、第1列コード・第2列名称が全件一致 |
| Userkabu構造 | 全4,289行が25列。第4列は4,240行で非ゼロ |
| 座標有効性 | 非ゼロ4,240値は全て1〜14,297。重複は0件 |
| 企業3ファイル | `kigyo.dat` は14,297×823 byte、`kigyo2.dat` と `kigyo3.dat` は各14,297×330 byte |
| 座標結合 | `p` を第4列値とすると、3ファイルの `(p - 1)` 番目レコードが同じ銘柄行に対応する候補座標になる |
| 例外 | 49行の第4列は0であり、企業3ファイルへの座標を得られない |
| `Zaimu.dat` | 69,407,205 byte。14,297件との単純固定長分割は成立せず、同一座標規則は未確定 |

## 直接証拠と否定した仮説

- 第4列の4,240値は重複なく企業3ファイルの共通レコード範囲に収まる。これは単なる行番号対応ではなく、`Userkabu.ini` に保持された明示的な座標候補である。
- `kigyo.dat` 先頭4 byteをリトルエンディアン整数として読んだ値は、現行銘柄コードと全件では一致しない。銘柄コード単独で企業レコードを検索する規則は採用しない。
- 銘柄名のCP932列が候補レコードに出現する事例は限定的で、固定の会社名欄又は全件照合キーとは確認できない。
- 旧版の同一レコード比較は複数候補を持つため、旧・現行の行番号又は完全一致だけで企業同一性を確定する規則は採用しない。

この台帳の各候補を通じても、49件を一意に対応させる根拠、候補座標の企業同一性、又は `Zaimu.dat` の財務キーは確認できなかった。これらを推測で補うことは指示書の禁止事項に抵触する。

4. 第4列が0の49銘柄についての企業・財務データの扱い。
