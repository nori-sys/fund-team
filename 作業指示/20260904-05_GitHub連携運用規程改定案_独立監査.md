## 05）監査観点

以下を独立して確認する。

### A. 目的適合性

- ChatGPT ↔ GitHub ↔ Codex の連携を正式運用へ移行する目的に適合しているか。
- GitHubをローカルWorkspace正本の代替ではなく、共有／履歴／参照ミラーとして扱う設計になっているか。

### B. 現行規程との整合

- `AGENTS.md` の権限・承認・外部共有・停止条件を弱めていないか。
- `START_HERE.md` の入口構造と正規場所停止ゲートを崩していないか。
- `AI間通信運用.md` の現行「外部共有対象外」と、新規GitHub共有層の関係が矛盾なく整理されているか。
- `フォルダ構成運用.md` の「同じ情報を複数の場所で正式管理しない」原則と整合しているか。
- ROLEの権限を暗黙に拡張していないか。

### C. 正本とミラー

- ローカルWorkspace側の規程を正本とする範囲が明確か。
- GitHub上の規程が参照用ミラーであることが明確か。
- GitHubミラーとローカル正本が不一致の場合の停止・判断手順が定義されているか。
- GitHub側の情報を正本と誤認する余地がないか。

### D. Publicリポジトリ安全性

現行 `nori-sys/fund-team` がPublicである前提で、以下を確認する。

- GitHubに載せてよい情報／載せない情報が十分明確か。
- 認証情報、APIキー、token、秘密鍵、個人情報、機密情報、重要資産が除外されているか。
- 作業指示や成果物に機密情報が混入した場合の停止条件があるか。
- Public/Privateの選択や公開範囲変更をAIが独断で行えない設計か。

### E. Git操作と承認境界

- commit / push / fetch 等の通常操作と、個別承認が必要な操作が区別されているか。
- force push、履歴改変、remote変更、認証方式変更、credential操作、公開範囲変更、新規リポジトリ作成等が適切に制限されているか。
- GitHub連携が既存Workspaceの未コミット変更や保護資産を損なう設計になっていないか。

### F. AI間通信との関係

- ChatGPT → GitHub → Codex の指示送達をAI間通信運用とどう位置付けるかが明確か。
- Codex → GitHub → ChatGPT の成果物／報告返送についても整合が取れているか。
- 送達、受領、承認、実行、完了の状態が混同されていないか。

### G. 変更範囲の妥当性

監査対象で示された以下の判断が妥当か確認する。

- 新規 `規程/WORKFLOW/GitHub連携運用.md`
- 最小変更 `AGENTS.md`
- 最小変更 `START_HERE.md`
- 最小変更 `規程/WORKFLOW/AI間通信運用.md`
- `フォルダ構成運用.md` は変更不要
- ROLE文書は変更不要

不要な規程変更や重複記述を増やしていないかも確認する。

### H. 未解決事項と承認境界

- 未解決事項が隠されていないか。
- Nori判断事項をAIが代替していないか。
- 正式発行前に必要な承認が明記されているか。

## 06）監査判定

カンは以下のいずれかを明示する。

- `適合（承認可）`
- `要修正`
- `監査不能`

`適合（承認可）` は内容面の発行推奨であり、正式規程への反映承認ではない。

`要修正` の場合は、最低限以下を示す。

- 対象箇所
- 根拠
- 影響
- 修正要求
- 再監査が必要な範囲

`監査不能` の場合は、監査不能理由とNori判断事項を示す。
