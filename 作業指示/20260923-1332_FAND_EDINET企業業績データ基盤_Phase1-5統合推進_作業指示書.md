## 01）目的・承認境界

EDINETをSOSIA FANDの企業業績データ基盤の主系統候補として、本番採用判断が可能な水準まで段階的に検証し、本作業内の候補仕様を設計・版固定し、本番資産から隔離した候補アーキテクチャを実装検証する。

Phase 1からPhase 5までを一つの原正式作業指示書に基づく一連の工程として扱う。本書がNoriにより正式承認・正式発行された場合に限り、後記の固定上限、開始前ゲート、Phase間移行ゲート、停止条件及び禁止事項の全範囲内で進行できる。正式発行前は、各Phase、実データ取得、認証情報利用、隔離領域作成又は実装を開始しない。

各Phaseは、主担当の「こう」による `実施 → 検証 → 是正` と、起案・実装・是正に関与していない独立監査担当「カン」による `独立監査 → 再監査` を分離する。カンは修正せず、こうが指摘を是正して再提出する。

当該Phaseの合格条件及び共通移行ゲートをすべて満たし、カンが「適合（承認可）」と判定し、停止条件に該当しない場合だけ、Noriへの逐次承認を求めず次Phaseへ移行できる。監査不能、要修正、ゲート未充足又は承認範囲外の事項が一つでもある場合は移行しない。

本作業内で確定する仕様、設計、コード及びDBはすべて本番候補であり、正式DBスキーマ、正式コード、正式設定又は正式運用への採用を意味しない。本番採否はPhase 5後にNoriだけが判断する。

### Phase 2：正規化データモデル候補仕様の版固定

Phase 1のゲート適合版成果物を基に、中核8セルの`accepted`と`hold`を同一モデル内で安全に保持し、Phase 4の必須機能を隔離環境で保存・検索・再評価・訂正追跡・出典確認できる最小論理データモデルを、本作業内の候補仕様として版固定する。網羅的なtaxonomy差、dimension/member及び企業固有拡張への完全対応は後続課題とする。正式DBスキーマ又は正式運用仕様として採用しない。

少なくとも、entity、source document / filing、fact、concept、context / period、value / unit、revision relation、provenance、validation state、hold reason、candidate group、confidence / evidence level（根拠区分であり数値スコアを要しない）、採用・非採用範囲、主キー・一意性を扱う。`hold`は値が存在しても採用値として扱わない。中核8セルの比較系列識別に必要な会計基準及び連結／単体を保持する。中核外の未確定属性は`unknown/null`として保持してよいが、採用セルの識別に必要な属性を未確定のまま採用しない。dimension/member、taxonomy版及び企業固有拡張の未対応範囲を記録し、データを推測補完しない。

公式根拠のない企業識別子有効期間等は推測で補完しない。

### Phase 3：取得・更新運用候補設計の版固定

Phase 4の隔離実装に必要な取得入力境界、更新・訂正追跡、再実行及び障害処理を、安全かつ再現可能な最小候補仕様として版固定する。本Phaseは設計及び隔離テスト計画までとし、自動取得、継続監視、本番運用、正式API設定又は正式ログ運用を開始しない。

少なくとも、版固定済み入力の取込み、再実行・重複防止・冪等性、訂正関係の記録、provenance、未確定候補の`hold`格納・後日の再判定、追加取得失敗・通信失敗・証跡不足を扱う正常な例外処理、障害・retryの上限と停止、秘密情報の非保存、RAWの承認済み取扱い、本番資産境界及びPhase 4必須機能の試験方法・閾値を扱う。新規提出の自動検知、taxonomy更新への完全追随及び網羅的な運用設計は後続課題とする。外部APIを用いる追加取得の権限は本改定で新設しない。

### Phase 4：本番候補アーキテクチャ隔離実装PoC

Phase 1～3でゲート適合し版固定した入力及び候補仕様を、本番資産から隔離したPoC専用DB・コードで実装する。必須検証範囲は、固定2社・2指標・2期間の中核8セルの`accepted`・`hold`、出典追跡、採用系検索での`accepted`限定、`hold`の安全保持・検索・理由と候補集合の追跡・後日の証跡追加による再評価・採用値への非混入、訂正前後や重複候補の誤自動採用防止、版固定入力による分類結果の再現・重複排除・冪等性及び安全上必要な異常系とする。実データの`accepted`が0件でも、`hold`処理・検索・再評価・安全隔離を検証できればPhase 4隔離実装PoCを実施できる。訂正実例が固定入力にない場合はテストダブルで取り違え防止を検証し、実データでの訂正対応成立と報告しない。taxonomy版差、dimension/member及び企業固有拡張の網羅的対応は必須検証範囲から外し、未対応範囲と本番採用前の課題として記録する。

Phase 4は原則としてPhase 1で承認範囲内に取得し、入力マニフェストで版固定した隔離入力だけを使用する。新たな外部書類取得又は対象追加は行わない。再取得試験は、隔離領域内の版固定入力又は応答を再現するテストダブルで実施する。

既存未コミット変更、未追跡資産及び他作業資産を変更、stage、commit、stash、reset、移動、削除又は本作業へ混入しない。非干渉確認に必要な最小限のパス及び状態メタデータは読取りできるが、内容は本作業上必要な別の承認根拠がない限り読まない。既存dirty状態を解消するためのpull、merge、rebase、reset、stash又は上書きを行わない。

### D. トークンコスト最適化と監査証跡

安全性、正確性、再現性、説明可能性及び監査可能性を損なわない範囲で、AIへの大量入力を避け、トークン消費を抑制する。トークン削減を、検証範囲、監査範囲又は必要証跡を減らす根拠にしない。

特にPhase 1及びPhase 4では、次を原則とする。

1. XBRL、CSV、JSON、DBレコード等の大量データをAIへ逐次全文投入して読解させない。
2. Python、SQLその他の決定論的処理で、抽出、集計、比較、差分検出、重複判定、件数集計、型検証等を先に行う。
3. AIには、機械処理で得られた要約、例外、差異、未知パターン、hold候補及び判断が必要な箇所を優先して提示する。
4. 正常・同型の大量事例は代表例と統計値で扱い、必要性なく全件を会話へ展開しない。
5. 再監査時は、変更のない大量データを再投入せず、差分・修正点・影響範囲を中心に監査する。
6. AIによる自然言語比較より機械的比較の方が再現性の高い処理は、原則として機械処理を優先する。
7. トークン削減を理由に、例外、失敗、hold、未確定事項又は安全上重要な証跡を省略しない。
8. 機械処理結果の妥当性は、代表サンプル、境界値、異常系等で検証し、集約処理自体の誤りを見逃さない。
9. 決定論的処理ごとに、入力範囲・件数、非公開入力マニフェスト又はハッシュ、スクリプト版・ハッシュ、設定、SQL又は抽出条件、実行環境版、出力件数、エラー・除外・hold件数及び前後件数照合を隔離証跡へ残す。
10. サンプリング基準、乱数種を使う場合の固定値、境界値及び異常系テストを記録し、母集団とサンプルの対応を追跡可能にする。
11. 差分再監査では、変更点、影響範囲及び不変部分の機械的照合結果を残す。

目的は「AIにすべて読ませること」ではなく、「AIを判断・設計・例外分析へ集中させること」とする。

### E. 機械処理とAI判断の分担

- 機械処理は、抽出、構文・型検査、件数集計、完全性照合、比較候補生成、差分検出、重複判定、再実行比較及びハッシュ照合を担当する。
- AIは、候補設計、例外分類候補、根拠整理、説明、調査優先順位及び監査指摘への是正案を担当する。
- AIの出力だけで、取得値、企業同一性、会計文脈、連結区分、会計基準、訂正関係、正規化採否又は本番採否を確定しない。公式根拠と決定論的証跡へ追跡できない事項は`hold`又は未確定とする。
- 機械処理コード自体を独立した正常系、境界値及び異常系テストで検証する。AIが生成又は変更したコードは、実行前レビュー、隔離環境での実行及びテストを必須とする。
- 機械処理の正常終了だけを合格根拠にせず、件数収支、例外、hold、除外及び代表サンプルを確認する。

### F. 自走原則と役割分離

作業途中に技術的課題、データ差異、設計上の問題又は監査指摘が発生しても、本指示書及び正式規程の範囲内で解決可能なら、

`調査 → 修正 → 再検証 → 独立再監査`

までCodex側で実施する。

「要修正」であることだけを理由にNoriへ戻さない。ただし、こうは監査判定を行わず、カンは起案、実装又は是正を行わない。監査不能又は停止条件該当時は自走しない。
