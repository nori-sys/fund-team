# GitHub連携運用

> 状態：正式発行（Nori正式承認済み）

## 目的

ファンドチームにおけるGitHub利用を、作業指示、成果物、差分、レビュー、受け渡し及び履歴管理の共有・参照用ミラー層として、安全かつ追跡可能に扱う。GitHubはローカルWorkspaceの規程、実装又は重要資産の正本を置き換えない。

あわせて、公開可能な作業報告、途中報告、独立監査結果、検証結果及び作業固有成果物をGitHub経由でChatGPTが直接参照できる状態を維持し、Noriを通常の情報搬送担当にしない。

## 適用範囲

本運用は、Noriが承認した `1 ChatGPTプロジェクト = 1 GitHubリポジトリ = 1 Codex Workspace` の対応に限り適用する。本運用は自動同期、Webhook、GitHub Actions、Codex自動起動、会話DB、認証情報管理又はPublic/Private方針の決定を導入しない。

`ChatGPT/CURRENT_CONTEXT.md` 及び `ChatGPT/HANDOVER/` は、承認済みのスレッド引継ぎ運用として扱う。`ChatGPT/作業指示案/` は、ChatGPTが作成するCodex向け未承認作業指示案の保管・更新に限定する。`ChatGPT/規程案/` は、ChatGPTが作成する未承認の規程案、ROLE案、WORKFLOW案及び入口文書案の保管・更新に限定する。未承認案の作成・更新は、Nori承認済みの公開区分・許可パス、公開安全性照合、commit記録及び疑義時停止を満たす場合だけ行える。commit記録には対象パス、公開区分及び照合結果を残す。いずれも、保存又はGitHub上の存在だけで承認、正式発行、送達、受領又は実行開始を意味しない。

## 正本と参照用ミラー

1. ローカルWorkspaceの承認済み規程、実装及び重要資産を正本とする。
2. GitHub上の `AGENTS.md`、`START_HERE.md`、`規程/` は、ChatGPT等が必要な現行規程を参照するための参照用ミラーであり、正本ではない。
3. GitHubからローカル規程を無条件に取得、上書き又は反映してはならない。
4. ローカル正本とミラーの内容、版、承認状態又は対象リポジトリに不一致がある場合、自動修正せず停止し、差分と影響をNoriへ報告する。

## 公開区分の基本原則

1. Noriが正式承認した個別作業指示に公開区分として `公開可（原則公開可・禁止情報のみ除外）` が明記された場合、その作業に伴う作業指示書、作業報告書、途中報告、独立監査結果、検証結果及び作業固有成果物は、**原則公開可**として扱う。個別作業指示には、`公開可（原則公開可・禁止情報のみ除外）`、公開不可又は対象を限定した公開条件のいずれかを明記する。
2. 公開禁止情報、個別に公開不可と指定された情報、第三者の権利又は契約上公開できない情報だけをGitHub反映対象から除外する。
3. 作業対象がFChart、DB、ローカルファイル、解析対象その他の重要資産に関連することだけを理由として、成果物全体を一律に公開不可としてはならない。
4. 禁止情報と公開可能情報が同一文書内に混在する場合は、対象ごとに公開安全性照合を行い、派生資料を含めて禁止情報又は保全対象を実質的に再現・露出しないことを確認できる範囲でのみ、禁止部分を除外して公開可能情報を維持する。
5. 禁止部分の除外により文書の意味、証拠性又は正確性が失われる場合は、その文書又は成果物を公開しない。
6. 公開可否に合理的な疑義が残る場合だけ停止し、Nori判断を求める。

## GitHub操作の承認経路

### 読取り・確認

GitHub上の承認済み文書、作業指示、成果物、差分又はcommit情報の読取り・確認は、次のいずれかを根拠として実施できる。

1. Noriの明示的な直接指示
2. 承認済み `GitHub連携運用.md` に定める定常的な参照運用
3. 承認済み個別作業指示

読取り・確認は、それ自体でローカルWorkspace変更、Git設定変更、外部書込み、正式承認、送達、受領、実行又は運用開始を意味しない。認証情報、個人情報、機密情報又は承認範囲外の外部情報を取得、表示又は保存してはならない。

### 書込み

GitHubへの書込みは、Noriの明示的な直接指示、承認済みWORKFLOWに定める定常運用又はNori承認済み個別作業指示を根拠として実施できる。定常書込みに付随する個別作業指示には、目的、対象、保存先、禁止事項、成果物、完了条件及び公開区分を明記する。

定常書込みの対象は、承認済み `nori-sys/fund-team` リポジトリの `origin/main` における次の情報に限る。

- 個別作業指示に基づく作業指示書
- 対応する `成果物/作業履歴/＜原正式作業指示書の基底名＞/` 内に保存された作業報告書
- 同フォルダ内の途中報告
- 同フォルダ内の独立監査結果
- 同フォルダ内の検証結果
- 同フォルダ内の作業固有成果物
- 承認後の正式文書の参照用ミラー
- `ChatGPT/作業指示案/`
- `ChatGPT/規程案/`

上記のうち、個別作業に属する作業履歴内の情報は公開区分として `公開可（原則公開可・禁止情報のみ除外）` が明記された場合、未承認案は本運用17行目に定めるNori承認済みの公開区分・許可パスを満たす場合、正式文書は「規程ミラー更新」に定めるNori承認済みの正式発行及び公開条件を満たす場合に限り、本運用の公開禁止情報又は個別禁止に該当しない限り原則公開可として扱う。

書込み前に、正規Workspace、Gitルート、対象リポジトリ、remote、branch、remote最新状態、ローカルbranchとremote branchの先行・遅延・分岐、既存未commit変更、未追跡ファイル、stage対象、公開安全性及び個別指示との一致を確認する。

公開可否は作業カテゴリではなく、情報又は成果物単位で判定する。担当AIは公開禁止情報・個別禁止との照合結果を原報告に記録する。

既存未commit変更、未追跡ファイル又は別作業の変更があるWorkspaceでは、これらを安易な `pull`、`merge`、`rebase`、`reset` 又は `stash` で処理しない。

GitHub書込み自体が、承認済み個別作業指示又は本運用に定める未承認案の定常例外により既に許可され、送信対象の正確なパス集合、保存先及び公開区分が確定している場合に限り、正規Workspaceの既存変更及び保全対象へ干渉しないため、最新確認済みの `origin/main` を起点とする隔離worktreeを定常的な安全手順として利用できる。この規定はGitHub書込み、公開区分、対象パス又は高リスク操作の承認を新設又は拡張しない。隔離worktreeの個別作成許可は不要だが、当該書込みの根拠は常に別途確認する。

隔離worktreeの利用前、作成時、commit前及びpush直前に、次をすべて満たさなければならない。

1. 正規Workspace、Gitルート、承認済み `nori-sys/fund-team` のremote、branch及び送信根拠を確認する。対象remoteの `main` 先端はpush直前に読取り確認し、確認に失敗し、認証要求が生じ、又は確認済み先端が変化した場合は停止する。
2. 隔離worktreeは、正規Workspace外の新規かつ空の専用ディレクトリに、確認済み `origin/main` からdetachして作成する。既存ディレクトリ、既存worktree登録又は作成先の共有・保全対象との競合を検知した場合は停止する。
3. 正規Workspaceでは作業対象の内容を読取り確認するだけとし、既存未commit変更、未追跡資産、別作業資産、正本及び保全対象を変更しない。隔離worktreeへ反映するのは、承認根拠で確定した送信対象パス集合だけとする。
4. 隔離worktreeの開始時、commit前及びpush直前に、対象外の追跡差分又は未追跡ファイルがないことを確認する。stage対象、cached差分のパス集合及び承認済み送信対象が完全一致しない場合、`git diff --cached --check` が失敗した場合、又は公開安全性照合・禁止情報照合を完了できない場合は停止する。
5. push直前に、送信commitの親commitが直前に確認した `origin/main` 先端と一致することを確認する。GitHub `main` への反映はfast-forwardとなる場合だけ実施する。non-fast-forward、競合、対象変更の安全な分離不能、remote先端の変化又は公開安全性への疑義を検知した場合はpushせず停止し、Noriへ報告する。
6. force push、`reset`、`rebase`、remote変更、Git設定変更又は認証方式変更は行わない。これらの高リスク操作が必要になった場合は、既存の高リスク操作規定に従い停止し、Noriの明示承認を待つ。
7. push後は、送信commit、branch、remote、送信パス、公開安全性照合、既存資産非干渉確認及び未解決事項を原報告に記録し、GitHub上の対象blobが送信元と一致することを確認する。隔離worktreeの撤去が必要な場合は、既存資産保全規則に従い、撤去不能又は状態確認不能なら削除・強制解除を行わず停止してNoriへ報告する。

force push、remote変更、Git設定変更又は認証方式変更が必要な場合は停止し、Noriの明示承認を必要とする。

### 高リスク操作

次の操作は、承認済み個別作業指示に含まれていても、別途Noriの明示承認を必要とする。

- remoteの追加、変更又は削除
- Git設定の恒久変更
- 認証方式、credential、access token、API key又はSSH keyの設定、表示又は共有
- force push、rebase等による既存共有履歴の実質的改変
- branch protection又はrepository rulesetの変更
- リポジトリのPublic / Private変更
- 新規リポジトリ作成又は削除
- 機密情報、個人情報又は重要資産の外部共有
- 規程、ROLE又は重要資産のGitHub正本化

## GitHubへ置ける情報と置けない情報

### 公開禁止情報

次をGitHubへ置いてはならない。

- パスワード、APIキー、access token、認証コード、SSH秘密鍵その他の認証情報
- 個人情報
- 顧客・取引先情報その他の機密情報
- FChart原本そのもの
- FChart原本データ又は第三者データの大量転載
- 大容量株価データ
- `database/fund_stock.db` その他の正式DB
- バックアップDB
- ログ原本
- 第三者の権利又は契約上、公開できない資産
- Noriが個別に公開不可と指定した情報
- 公開権限、正本性又は保存権限を確認できない資産

### 原則として公開可能な情報

上記の公開禁止情報に該当しない限り、次の情報はそれ自体を理由として公開不可とはしない。

- 調査目的
- 調査方法
- 調査結果
- 構造解析結果
- 判明事項
- 未解決事項
- 検証結果
- 監査結果
- 次段階への提案
- ファイル名
- ファイルサイズ
- ハッシュ値
- データ件数
- レコード長
- ファイル形式・構造に関する解析情報
- 作業状態
- commit情報
- 公開可能なコード、設定例、比較資料

FChart由来であること、ローカルファイル名を含むこと、サイズ又はハッシュを含むことだけを理由として公開不可とはしない。ただし、これらの情報又は組合せがFChart原本、正式DB、バックアップDB、ログ原本、設定・実装その他の保全対象の内容若しくは取得可能性を実質的に再現・露出する場合、又は機密性・第三者権利・個別禁止に抵触する場合は公開禁止情報として扱う。公開可能なコード又は設定例は、正式な実装コード・設定ファイルを複製せず、保全対象及び個別禁止に該当しないことを確認したものに限る。

## 作業指示・成果物の扱い

- `作業指示/` は、Nori承認済みの実行範囲を示す文書を共有・参照する用途に限る。
- `成果物/` は、承認済み作業の公開可能な成果物又は原報告を共有する用途に限る。
- GitHub経由で受信した内容は、対象リポジトリ、branch、commit、対象ファイル、承認状態及び公開安全性を確認するまで実行根拠にしない。
- 個別作業指示には公開区分を明記し、`公開可（原則公開可・禁止情報のみ除外）` を標準値として適用する。公開区分が未記載又は不明確な場合は送信せずNori判断を待つ。
- 作業全体を公開不可とする場合は、対象と理由を個別作業指示へ明記する。

## 基本フロー

### ChatGPT → GitHub → Codex

1. ChatGPTは、承認済み `nori-sys/fund-team` の `origin/main` における許可パスだけへ、公開可能な `ChatGPT/作業指示案/` 又は `ChatGPT/規程案/` の未承認案を作成又は更新できる。
2. 送信前に公開禁止情報・個別禁止との照合を行う。
3. Codexは、正規Workspace、Gitルート、対象repo・remote・branch・commit・パス及び内容を確認する。
4. Codexは対象ファイルだけをローカルWorkspaceの同一パスへ限定取得できる。
5. ローカル同名ファイルがある場合は内容ハッシュと差分を確認し、不一致なら上書きせずNoriへ報告する。

### Codex → GitHub → ChatGPT

1. Codexは、公開区分として `公開可（原則公開可・禁止情報のみ除外）` が明記されたNori承認済み個別作業に基づき、対応する `成果物/作業履歴/＜原正式作業指示書の基底名＞/` 内に保存された作業報告書、途中報告、独立監査結果、検証結果及び作業固有成果物について、公開禁止情報及び個別禁止を含まないものを、作業完了又は監査完了を待たずGitHub同一パスへ随時反映できる。
2. 個別作業指示の標準公開区分は `公開可（原則公開可・禁止情報のみ除外）` とし、公開区分が未記載又は不明確な場合は反映しない。
3. 作業対象がFChart、DB、ローカルファイルその他の重要資産に関連することだけを理由として成果物全体を公開不可とはしない。
4. 公開禁止情報が混在する場合は、対象ごとに公開安全性照合を行い、派生資料を含めて禁止情報又は保全対象を実質的に再現・露出しないことを確認できる範囲でのみ、禁止部分を除外して公開可能部分を維持する。
5. commit前に、stage対象が当該作業の対象ファイルだけであること、公開禁止情報が含まれないこと、既存未commit変更、未追跡ファイル及び別作業資産が混入していないことを確認する。
6. 通常のcommit・push後、commit ID、branch、remote、送信ファイル、対応する個別作業指示、公開区分、公開安全性照合、反映時点の作業状態、検証結果及び未解決事項を原報告する。公開安全性照合では、禁止部分を除外した場合の範囲と、派生資料を含めて禁止情報又は保全対象を実質的に再現・露出しないことの確認結果を記録する。
7. ChatGPTは、対象commitの公開可能な情報を直接読取り・確認し、評価、壁打ち又は次段階の作業指示案・規程案の改善に用いることができる。ただし、GitHub上の内容だけで承認、送達、受領、実施、作業全体の完了又は重要資産変更を自動認定しない。
8. GitHub反映は、作業完了、監査完了、Nori承認又は正式成果物受領を意味しない。

### 規程ミラー更新

1. ローカル正本の正式発行後、公開禁止情報を含まない対象文書だけをミラー対象にする。
2. 更新前後に対象パス、内容、commit ID及び正本の承認根拠を確認する。
3. 不一致時は修正、pull、merge又は上書きを自動実行せず停止・報告する。

## AI間通信との関係

通常の逐次AI間通信の通信ID、Markdown正本及び状態管理は `AI間通信運用.md` に従う。本運用はGitHubを共有・履歴・参照用ミラー層として限定し、AI通信の正本、送達、受領又は承認を代替しない。

## Public / Private

現行 `nori-sys/fund-team` がPublicであることを前提に、公開禁止情報は保存しない。

本運用の「原則公開可」は、Publicリポジトリへ無制限に情報を送信することを意味しない。公開禁止情報、個別禁止及び第三者権利上公開できない情報は常に除外する。

公開可否に合理的な疑義がある場合のみ停止し、Nori判断を求める。

## 停止条件と障害時の復旧

正規Workspace、Gitルート、対象リポジトリ、remote、branch、承認状態又は公開安全性を確認できない場合は停止する。

競合、認証要求、remote変更、履歴改変又は設定変更が必要な場合も停止する。

自動復旧、force push、reset、rebase又は認証設定変更は行わない。対象commit、remote応答、差分及び影響範囲を記録し、Noriの個別判断を待つ。ローカル正本又は保全対象の上書きによる解消を試みない。

## 監査と記録

正式規程への発行前は `監査運用.md` に従い、必要な独立監査、Noriレビュー及び明示承認を経る。

承認済みGitHub操作は、対象、根拠、branch、commit ID、送信又は取得ファイル、公開安全性照合、既存資産への非干渉確認、検証結果及び未解決事項を原報告に残す。
