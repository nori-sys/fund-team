# SOSIA FAND GitHub経由報告共有 標準運用改定案

## 00）状態・対象・承認境界

- 状態: 未承認のWORKFLOW改定案
- 目的: `ChatGPT ↔ GitHub ↔ Codex` 間で公開可能な途中報告を直接参照できるようにし、Noriを通常のコピー・貼付け・情報搬送から外す。
- 改定対象: `規程/WORKFLOW/指示書・報告書運用.md` および `規程/WORKFLOW/GitHub連携運用.md` のみ。
- 改定しない対象: `AGENTS.md`、`START_HERE.md`、ROLE、`AI間通信運用.md`、正本・DB・バックアップ・ログ・設定・実装コード・外部FChart原本。
- 承認境界: 本案、GitHub上の保存、commit又は独立監査の `適合（承認可）` は、正式発行、運用開始、個別作業の承認、成果物受領又は作業全体の完了を意味しない。正式反映はNoriの明示承認後に限る。

## 01）改定目的

承認済み個別作業指示に基づく長期・継続作業について、Noriが `公開可` と判断した対象だけを、完了前でも作業履歴からGitHubへ反映できるようにする。ChatGPTは反映済みの途中報告、独立監査結果、検証結果及び公開可能な作業固有成果物をGitHubから直接参照し、評価、壁打ち及び次段階の案の改善に用いる。

この共有は参照用ミラー層に限る。AI間通信のMarkdown正本、送達、受領、承認、正本又は自動実行を代替しない。

## 02）共通の安全条件

途中報告をGitHubへ反映できるのは、すべて次を満たす場合に限る。

1. 対応するNori承認済み個別作業指示に、目的、対象、保存先、禁止事項、成果物、完了条件及び当該反映対象の公開区分 `公開可` が明記されている。
2. 対象は当該作業の `成果物/作業履歴/＜原正式作業指示書の基底名＞/` に保存された、途中作業報告書、独立監査結果、検証結果又は作業固有成果物である。
3. FChart原本、大容量株価データ、正式DB、バックアップDB、ログ原本、認証情報、個人情報、顧客・取引先情報、機密情報、公開可否・正本性・保存権限が未確定の資産及び個別禁止対象を含まない。
4. 正式コード、正式設定、正式規程、ROLE、WORKFLOWその他の既定配置先を持つ資産を、作業履歴へ複製して反映対象としていない。
5. 現行 `GitHub連携運用.md` の正規Workspace・Gitルート・対象repo/remote/branch・remote最新状態・差分・stage・公開安全性・既存資産非混入の確認及び停止条件を満たす。

公開可否に疑義、未分類又は個別禁止がある場合は反映せず、Noriの判断を待つ。GitHubへの途中報告反映は、作業完了、監査完了、Nori承認、正式成果物の受領、実装・分析結果の確定又は権限拡大を意味しない。

## 03）条文改定案: `指示書・報告書運用.md`

次の3節を、それぞれ現行本文と置換する。他の節は変更しない。

### 07）作業報告書（置換後全文）

Codexは、承認済みの個別作業指示に基づく作業結果を原報告として作業報告書にまとめる。作業報告書は、正式承認、送達、成果物の受領又は作業全体の完了を意味しない。

作業報告書は、対応する作業履歴フォルダへ保存する。1通目は `YYYYMMDD-HHMM_プロジェクトID_件名_作業報告書.md`、同一作業指示に対する第2報以降は `YYYYMMDD-HHMM-NN_プロジェクトID_件名_作業報告書.md` とする。`NN` は同一作業指示に対する報告連番とする。既存の報告書を上書きせず、途中報告、再報告、差戻し後の報告及び再監査後の報告は新しい報告書として保存する。作成前に同名ファイルがないことを確認し、重複時は新たな報告連番を使用する。

途中報告は、対応する個別作業指示、報告時点、実施済み事項、未実施事項、検証済み事項、未解決事項、公開区分及び「作業完了・監査完了・Nori承認・正式成果物受領を意味しない」旨を明記する。途中報告を作成又はGitHubへ反映しても、作業状態又は承認状態を推測で更新してはならない。

### 09）基本フロー（置換後全文）

```text
ChatGPT
  ↓
ChatGPT/作業指示案/
  ↓ Nori正式承認・発行
作業指示/
  ↓
Codex実行
  ↓
成果物/作業履歴/＜指示書基底名＞/
  ↓
作業報告書・独立監査結果・検証結果・作業固有成果物
  ↓ 公開可の対象だけは、完了前を含めGitHubへ随時反映可
GitHub（参照用ミラー）
  ↓
ChatGPTによる直接参照・評価・壁打ち・案の改善
  ↓ 必要な判断のみ
Noriの正式承認・完了認定（必要な場合）
```

正式配置先を持つ成果物については、Codex実行時に承認された配置先へ保存する。途中報告の反映可否及びGitHub経由の参照は、`GitHub連携運用.md` の安全条件・公開区分・停止条件に従う。

### 10）GitHub連携（置換後全文）

GitHubへの作業指示書案・作業報告書・独立監査結果・検証結果・作業固有成果物の受け渡しは、`GitHub連携運用.md` に従う。標準フローは、`ChatGPT/作業指示案/` 上の未承認案をGitHub経由で対象ファイルだけ限定取得し、ローカル同一パスへ新規作成すること、ならびに承認済み個別作業の作業履歴内に保存された `公開可` の途中作業報告書、独立監査結果、検証結果及び当該作業固有成果物だけをGitHub同一パスへ随時反映することである。GitHub上の配置又は存在だけで、ローカル正本の承認状態、正式発行、送達、受領、実行開始、作業完了又は監査完了を推測しない。

個別作業指示には、目的、対象、保存先、制約・禁止事項、成果物、合格条件・完了条件及び公開区分を必ず記載する。作業報告書の作成場所、命名規則、途中報告に必要な状態表示、公開安全性確認、stage確認、既存資産混入防止、non-fast-forward時の停止、force push禁止、remote・Git設定・認証方式の無断変更禁止及びcommit ID等の原報告記録は承認済みWORKFLOWに従う通常動作とし、毎回の重複記載を要しない。GitHub定常運用を停止又は変更する場合は、その例外を個別作業指示へ明記する。

Publicリポジトリへ保存できない情報、機密情報、個人情報、大容量データ、DB本体その他の禁止対象を、作業履歴フォルダへ保存することでGitHub公開可能として扱ってはならない。正式DB、正式コード、正式設定、正式規程、ROLE、WORKFLOWその他の既定配置先を持つ資産は、作業履歴へ重複コピーしてGitHubへ送信しない。作業履歴フォルダ又はGitHub上の途中報告の存在は、成果物の正式承認、作業完了、監査完了又はNori承認を意味しない。

## 04）条文改定案: `GitHub連携運用.md`

次の「Codex → GitHub → ChatGPT」を現行本文と置換する。他の節は変更しない。

### Codex → GitHub → ChatGPT（置換後全文）

1. Codexは、目的、対象、保存先、禁止事項、成果物、完了条件及びNori承認済みの公開区分を定める個別作業指示に基づく作業について、作業完了又は監査完了を待たず、作業履歴内に保存された `公開可` の途中作業報告書、独立監査結果、検証結果及び当該作業固有成果物だけを同一パスへ反映できる。反映対象は、公開安全性確認を完了し、「反映は作業完了・監査完了・Nori承認・正式成果物受領を意味しない」ことを明記したものに限る。
2. commit前に、stage対象が承認済みの公開可ファイルだけであること、機密情報及び禁止対象が含まれないこと、既存未commit変更・未追跡ファイル・別作業資産が混入しないことを確認する。公開可否に疑義、未分類又は個別禁止がある場合は送信しない。
3. 通常のcommit・push後、commit ID、branch、remote、送信ファイル、対応する個別作業指示、公開区分、公開安全性照合、反映時点の作業状態、検証結果及び未解決事項を原報告する。反映時点の作業状態は事実として記録し、承認又は完了を推測で記録しない。
4. ChatGPTは、対象commitの公開可能な情報を直接読取り・確認し、評価、壁打ち又は次段階の作業指示案・規程案の改善に用いることができる。ただし、GitHub上の内容だけで承認、送達、受領、実施、作業全体の完了又は重要資産変更を自動認定しない。

## 05）整合上の明確化

- AI間通信の正本、通信ID、送達及び受領の扱いは `AI間通信運用.md` を変更しない。
- `ChatGPT/規程案/` は未承認案の保存先であり、本案の修正・監査・GitHub上の存在は正式規程、ROLE又はWORKFLOWの変更権限を与えない。
- GitHubの参照用ミラーとしての位置付け、Publicリポジトリでの疑義時停止、remote変更・認証変更・force push等の高リスク操作にNori明示承認を要する条件は変更しない。
- Noriは、正式承認、方針変更、権限拡大、安全停止、重要資産変更その他の人間判断が必要な事項だけを判断する。通常の公開可途中報告の搬送・参照をNoriのコピー・貼付け作業に依存させない。

## 06）正式反映前の確認事項

本案が独立監査で `適合（承認可）` となった後も、Noriが対象2文書への正式反映・正式発行を明示承認するまで、現行WORKFLOWは変更しない。正式反映時は、改定後の完全な2文書を作成し、Nori承認内容と一致すること、正規Workspace、保存先、既存資産への非干渉及び公開条件を確認する。
