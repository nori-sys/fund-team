## 背景

会社情報DB構築、とくに0217 IRBANK工程で、
- v2 → v3 → v4
- ACL追加
- 親階層ACLの理論上の残存リスク
のように局所是正と監査が反復し、Noriの時間・トークン消費に対して作業進捗が不十分となった。

現行規程には、停滞時の自己診断、条件緩和、上位条件再設計の規定がすでにあったが、強制ゲートとして機能していなかった。

このため0217技術作業を一時停止し、制御系を再設計した。

## 新設計の基本方針

会社情報データベース構築に限り、通常工程ではカン独立監査を標準としない。

標準フロー：
「起案・実装 → こうの実装後自己検証 → 次工程」

カン独立監査は高リスク工程・正式な節目に限定する。

### A/B/Cリスク分類

A：重大安全リスク
- データ喪失
- 不可逆な重要資産毀損
- 機密・認証・個人情報漏えい
- 無承認外部公開
- 重大なDB破壊等
→ 停止し、必要に応じカン監査・Nori判断へ。

B：成果品質重大リスク
→ こうが承認範囲内で是正し、自己検証を再実施。

C：非阻害残存リスク
- 理論上の可能性
- 軽微な不確実性
- 現在の目的達成を阻害しない残存リスク
→ 記録するが、それだけを理由に停止しない。

### 停滞強制ゲート

次のいずれかで発火。
- 同系統の停止・要修正・監査不能が2回
- 同じ目的の正式文書改定が2回
- 同系統追加調査2回で主要成果改善なし
- 採用0件・全件hold等、主要成果が改善しない状態が継続

発火後は同系統の局所修正・追加調査・追加監査を停止。
3周目へ進まず、目的・完了条件・検証条件・監査条件・安全条件まで遡って再診断し、Noriへ条件緩和又は上位条件再設計案を一括提示する。

## 重要な運用原則

今回の再設計の目的は「監査を甘くすること」ではなく、
重大事故防止に必要な安全性を維持したまま、理論上の軽微な残存リスクや局所是正反復によって会社情報DB構築が停止し続ける構造を除去すること。

同系統の停止が2回に達した場合は、規程どおり停滞強制ゲートを発火し、3周目の局所修正へ進まない。
