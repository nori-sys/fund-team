## 01）目的

SOSIA FANDにおけるCodex側の作業を、Noriによる途中中継を必要最小限にしつつ、安全性、独立監査、既存資産保全およびGitHub同期安全性を維持したまま自律完結できる運用へ整理する。

今回の改訂では、特に次を規程上で明確化する。

1. `こう → カン → こう修正 → カン再監査` の自律監査ループ
2. Nori判断が必要な停止条件と、Codex側で継続可能な範囲の分離
3. `ChatGPT/作業指示案/` の正式な位置付け
4. ChatGPTが作成する未承認作業指示案のGitHub保存運用
5. GitHub書込み前のremote最新状態確認、先行・遅延・分岐確認
6. 既存未コミット／未追跡資産の保全
7. ChatGPTとCodexが同一GitHubリポジトリを利用する前提での同期安全ルール

## 03）前提

- GitHubリポジトリ: `nori-sys/fund-team`
- branch: `main`
- GitHub上の規程はローカルWorkspace正本の参照用ミラーであり、正本ではない。
- 正式規程、ROLE、WORKFLOWの変更確定権限はNoriにある。
- `適合（承認可）` はNoriの正式承認を代替しない。

- 今回はWebhook、GitHub Actions、MCP、Codex自動起動、自動監視等を導入しない。

## 04）改訂要件

### A. Chief Manager「こう」の自律完結範囲

承認済み作業指示の目的、対象、制約、成果物、完了条件、禁止事項および権限を変更しない範囲で、こうが実行方法、作業順序、必要な調査、修正、再提出を自律的に進められることを明文化する。

Nori判断が不要な軽微な修正、監査指摘への是正、再検証について、途中承認を必須としない。

一方、次のような事項は停止し、Nori判断へ上げる。

- 承認済み範囲の拡張・変更
- 正式規程、ROLE、権限体系そのものの確定変更
- 重要資産への重大変更
- 削除、上書きその他の不可逆操作
- 外部公開条件の変更
- 機密情報、認証情報、個人情報の取扱い変更
- 解消不能な規程矛盾
- 重大な安全・資産保全リスク

### B. 自律監査ループ

Noriが独立監査を指定した作業では、承認済み範囲内に限り次を標準ループとする。

`こうが案作成・実装 → カン監査 → 要修正ならこうが是正 → カン再監査`

これを `適合（承認可）` まで反復できるようにする。

カンは次を守る。

- 起案しない
- 実装しない
- 是正しない
- 監査対象の目的や承認範囲を拡張しない
- 判定と根拠を明示する

Nori判断事項が発生した場合、その部分は停止する。ただし、判断事項と独立して安全に継続可能な是正・検証まで一律停止させないよう整理する。

### C. `ChatGPT/作業指示案/` の位置付け

次を規程上で明確にする。

- ChatGPTが作成したCodex向け未承認作業指示案の保存場所である。
- 保存されているだけでは承認・発行・送達・実行開始を意味しない。
- Noriが正式承認した後にのみ、正式な `作業指示/` 運用へ移行する。
- 正式規程、ROLE、WORKFLOW、正式成果物の保存場所として使用しない。

READMEの現行趣旨を維持し、規程側から矛盾なく参照できる形にする。

### D. ChatGPTのGitHub書込み範囲

ChatGPTについて、次の2系統を区別する。

1. スレッド引き継ぎ運用として既承認の `ChatGPT/CURRENT_CONTEXT.md` および `ChatGPT/HANDOVER/`
2. 未承認作業指示案の作成・更新用 `ChatGPT/作業指示案/`

`ChatGPT/作業指示案/` への書込みは、未承認案の保管に限定し、正式規程や重要資産の変更権限へ拡張しない。

### E. GitHub書込み前のremote確認

CodexがGitHubへ書込む前に、少なくとも次を確認する標準を設ける。

- 正規Workspace
- Gitルート
- 対象repository
- remote
- branch
- remote最新状態の取得・確認
- ローカルbranchとremote branchの先行／遅延／分岐状態
- 既存未コミット変更
- 未追跡ファイル
- stage対象
- 公開安全性
- 承認済み作業指示との一致

`ローカルmain = GitHub main` を常に仮定してはならない。

### F. 既存資産・未コミット変更の保全

既存未コミット変更、未追跡ファイル、別作業の変更が存在する場合、それらを安易な `pull`、`merge`、`rebase`、`reset`、`stash` 等で処理しないことを明確化する。

必要に応じて一時branch、一時worktree等により隔離して処理する考え方を採用できるようにする。

ただし、具体的方法は目的型指示の範囲内で担当AIが選択し、既存資産を変更・消失させないことを優先する。

### G. GitHub同時利用時の分岐対策

ChatGPTがGitHub `main` を更新し、Codexローカル `main` が追随していない場合に、non-fast-forward等が発生しうることを前提とする。

競合または分岐を検知した場合、対象変更だけを安全に分離できない限り、無理に同期・統合しない。

remote変更、force push、共有履歴の実質改変、認証方式変更など既存の高リスク操作は、従来どおりNoriの明示承認対象とする。

## 05）作業方法

この作業の実行がNoriに正式承認された後、こうは次を行う。

1. ローカル正本とGitHubミラーの対象4文書を確認する。
2. 不一致がある場合、推測で統合せず差分を報告する。
3. 対象4文書の改訂案を作成する。
4. 正式版を直接確定・上書きせず、監査可能な改訂案として提示する。
5. カンへ独立監査を依頼する。
6. `要修正` の場合、承認済み範囲内でこうが是正し、再監査へ回す。
7. `適合（承認可）` まで反復する。
8. `適合（承認可）` 後、完全な最終改訂案、変更点、未決事項をNoriへ提出する。
9. Noriが正式反映を承認するまで、正式規程への確定反映は行わない。

## 07）完了条件

- 対象4文書の改訂案が完成している。
- 4文書間に意図しない矛盾、重複、抜け、権限衝突がない。
- カンの最終判定が `適合（承認可）` である。
- 正式規程、ROLE、WORKFLOWへ未承認変更を加えていない。
- 既存未コミット変更・重要資産を毀損していない。

- Noriが確認すべき事項が明示されている。

この完了は、正式規程への反映完了を意味しない。

## 09）停止条件

次の場合は、影響範囲を整理してNoriへ報告し、該当部分を停止する。

- ローカル正本とGitHubミラーの重要な不一致
- 承認範囲を超える変更が必要
- 正式権限体系そのものの追加変更が必要
- 重大な規程矛盾を解消できない
- 重要資産保全に疑義がある
- remote／branch／Gitルートを安全に確定できない
- 認証変更、force push、共有履歴改変等が必要
- Publicリポジトリへの公開可否が不明

停止条件に該当しない範囲は、承認済み目的達成まで自律的に進める。
