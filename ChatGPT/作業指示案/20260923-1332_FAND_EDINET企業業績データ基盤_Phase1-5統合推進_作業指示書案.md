# FAND EDINET企業業績データ基盤 Phase1-5統合推進 作業指示書案

> 状態：未承認案  
> 公開区分案：公開可（原則公開可・禁止情報のみ除外）

## 01）目的

EDINETをSOSIA FANDの企業業績データ基盤の主系統候補として、本番採用判断が可能な水準まで段階的に検証・設計・隔離実装する。

Phase 1からPhase 5までを一連の開発工程として扱い、Noriによる判断、正式承認、認証情報等の入力が必要な事項を除き、Codex側で可能な限り自律的に進行する。

各Phaseは原則として、

`実施 → 検証 → 独立監査 → 要修正時の是正 → 再監査 → 適合`

までCodex側で完結させる。

独立監査で「適合（承認可）」となり、次Phaseへの移行が本指示書の承認範囲内である場合は、Noriへの中間確認を求めず次Phaseへ進む。

---

## 02）対象・範囲

### Phase 1：横断拡張PoC

0213最小PoCで成立した正規化方式について、企業・業種・会計基準・連結区分・年度・taxonomy・dimension/member・企業固有拡張・訂正文書等の差異に対する一般性を検証する。

対象企業・書類・件数は固定せず、一般性評価に必要十分な最小範囲をCodex側で選定する。

少なくとも次を検証軸とする。

- 日本基準／IFRS等
- 連結／単体
- 複数業種
- 複数事業年度
- taxonomy version差
- dimension/member差
- 企業固有拡張要素
- 訂正文書又は訂正関係
- 当期／比較期

### Phase 2：正規化データモデル仕様確定

Phase 1の結果を基に、EDINET由来企業業績データの論理データモデルを確定する。

少なくとも次を扱う。

- entity / entity identifier
- source document / filing / revision
- fact / context
- accounting standard
- consolidated / standalone
- period
- taxonomy / concept
- unit / decimals
- value type / sign
- dimension / member
- provenance
- validation state
- hold / unresolved state

公式根拠のない企業識別子有効期間等は推測で補完しない。

### Phase 3：取得・更新運用設計

EDINETからの取得・更新・訂正追跡・再取得を、安全かつ再現可能に運用する設計を確定する。

少なくとも次を扱う。

- 新規提出・訂正文書の検知
- 再取得・重複防止・冪等性
- API障害・retry
- APIキー管理
- RAWの一時利用・保存方針
- provenance
- taxonomy更新
- validation / hold
- ログ・障害復旧
- 本番資産境界

### Phase 4：本番DB隔離実装PoC

Phase 1～3で確定した仕様を、本番資産から隔離したDB・コードで実装し、複数企業・複数年度・訂正・再取得・重複排除・taxonomy差・provenance・hold・検索・異常系・冪等性を検証する。

正式DB、正式コード、正式設定、本番運用、FChart原本その他の重要資産には変更を加えない。

### Phase 5：本番採用判断資料作成

Phase 1～4の結果を統合し、Noriが

- 採用する
- 追加検証する
- 採用しない

を判断できる資料を作成する。

本番採用、本番DB変更、正式コードへの反映、自動運用開始は実施しない。

## 04）制約・禁止事項

### A. Nori判断が必要な停止条件

次の場合のみ停止し、Noriへ判断又は入力を求める。

- 本番DBへの書込み・変更
- 正式コード、正式設定又は正式運用への採用
- API、サービス等の新規契約・課金
- 新たな認証情報、APIキー等の発行又はNoriによる入力が必要
- EDINET等の利用条件について本番利用可否の判断が必要
- 重要資産への重大変更
- 正式規程、ROLE、WORKFLOWの変更
- 個人情報、機密情報、第三者権利等に関するNori判断が必要
- 当初目的又は承認範囲の実質的変更
- 安全性、正本性又は公開可否を確認できない
- Phase 5における本番採用・不採用の最終判断

これら以外の技術的方法、対象企業、検証件数、内部データ構造、テスト方法等は、承認済み規程と本指示書の範囲内でCodex側が判断する。

### B. トークンコスト最適化原則

安全性、正確性、再現性及び説明可能性を損なわない範囲で、AIへの大量入力を避け、トークン消費を抑制する。

特にPhase 1及びPhase 4では、次を原則とする。

1. XBRL、CSV、JSON、DBレコード等の大量データをAIへ逐次全文投入して読解させない。
2. Python、SQLその他の決定論的処理で、抽出、集計、比較、差分検出、重複判定、件数集計、型検証等を先に行う。
3. AIには、機械処理で得られた要約、例外、差異、未知パターン、hold候補及び判断が必要な箇所を優先して提示する。
4. 正常・同型の大量事例は代表例と統計値で扱い、必要性なく全件を会話へ展開しない。
5. 再監査時は、変更のない大量データを再投入せず、差分・修正点・影響範囲を中心に監査する。
6. AIによる自然言語比較より機械的比較の方が再現性の高い処理は、原則として機械処理を優先する。
7. トークン削減を理由に、例外、失敗、hold、未確定事項又は安全上重要な証跡を省略しない。
8. 機械処理結果の妥当性は、代表サンプル、境界値、異常系等で検証し、集約処理自体の誤りを見逃さない。

目的は「AIにすべて読ませること」ではなく、「AIを判断・設計・例外分析へ集中させること」とする。

### C. 自走原則

作業途中に技術的課題、データ差異、設計上の問題又は監査指摘が発生しても、本指示書及び正式規程の範囲内で解決可能なら、

`調査 → 修正 → 再検証 → 独立再監査`

までCodex側で実施する。

「要修正」であることだけを理由にNoriへ戻さない。

## 06）合格条件・完了条件

### Phase 1
複数条件で正規化モデルの成立範囲と破綻条件を説明でき、Phase 2の論理データモデル設計に必要な情報が揃っている。

### Phase 2
異なる企業・年度・taxonomy・訂正関係を、情報損失や推測補完なしに扱える論理モデルが成立している。

### Phase 3
取得から正規化、訂正、再取得までを安全かつ再現可能に運用できる設計が成立している。

### Phase 4
隔離環境で本番候補アーキテクチャが仕様どおり機能し、データ保全、再現性、訂正追跡、異常処理、冪等性を確認できる。

### Phase 5
Noriが追加の調査指示を自ら設計しなくても、本番採用・追加検証・不採用の判断に必要な情報が揃い、最終独立監査が「適合（承認可）」となっている。

Phase 5の独立監査「適合（承認可）」時点で停止し、本番採用判断はNoriへ上げる。

---

## 07）公開区分

公開可（原則公開可・禁止情報のみ除外）。

公開可能な作業報告書、監査結果、検証結果その他の成果物は、承認済みGitHub連携運用に従って随時参照用ミラーへ反映できる。

認証情報、APIキー、RAW原文、第三者権利上公開できないデータ、本番DBその他の公開禁止情報は反映しない。

---

## 08）通常運用からの例外

Phase 1からPhase 5までを一つの承認範囲として扱い、各Phaseの「適合（承認可）」後にNoriの逐次承認を求めず、次Phaseへ自動的に進行できることを本作業固有の例外とする。

ただし、本書04）Aの停止条件に該当する場合及びPhase 5の本番採用判断は必ずNoriへ上げる。
