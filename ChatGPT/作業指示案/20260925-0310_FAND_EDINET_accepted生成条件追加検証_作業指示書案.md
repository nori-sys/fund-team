# FAND EDINET accepted生成条件追加検証 作業指示書案

> 状態：未承認案・実行禁止
> 公開区分案：公開可（禁止情報・実データ等を除外）

## 01）目的

1332「FAND EDINET企業業績データ基盤 Phase1-5統合推進」で実入力654候補がすべて`hold`となり、`accepted`が0件となった結果を受け、EDINET公式情報から企業業績値を`accepted`と判定するために必要な**公式根拠、識別条件及び判定規則**を追加検証する。

目的は`accepted`件数を増やすことではない。

公式根拠によって安全かつ再現可能に一意採用できる場合だけ`accepted`とし、根拠不足の場合は`hold`を維持する。

最終的に、

- どの条件を満たせば`accepted`にできるか
- 現行データ・証跡でその条件を満たせるか
- 満たせない場合、何が不足しているか
- 追加取得又は追加実装が必要か

を明確にする。

## 02）対象・範囲

### 基礎資料

1332正式作業及び対応成果物を基礎資料とする。

特に次を優先参照する。

- Phase 1～4の版固定成果物
- Phase 1～4統合報告
- Phase 5本番採用判断資料
- Phase 5最終独立監査結果
- 654候補の分類結果
- 中核8セルの候補集合及びhold理由
- Phase 4隔離PoCのデータモデル・判定機構

### 検証対象

主として次を検証する。

1. 業績指標とXBRL conceptの対応根拠
2. concept QName、taxonomy、企業固有拡張要素の扱い
3. context / periodによる当期・比較期の識別
4. 連結／単体の識別根拠
5. 日本基準／IFRS等の会計基準識別
6. dimension / memberが採否へ与える影響
7. 重複factの一意選択条件
8. 訂正前後の優先関係
9. value、unit、nil、符号等の採用条件
10. provenance及び公式根拠の最低要件
11. `accepted` / `hold` / `rejected`の境界条件

1332の中核8セルを優先して使用し、必要性なく対象企業・年度・指標を拡大しない。

## 04）制約・禁止事項

### A. 判定原則

- `accepted`を作るために根拠を推測・補完しない。
- AIの意味解釈だけを公式根拠として採用しない。
- 公式資料及び決定論的証跡へ追跡できない事項は`hold`を維持する。
- `accepted`件数を合格条件にしない。
- 既存の`hold`を根拠なく解除しない。

### B. 調査範囲

まず1332で保存・版固定済みの入力、証跡及び公式資料を最大限再利用する。

追加調査が必要な場合は、EDINET又は金融庁等の**公式公開仕様・技術資料・taxonomy関連資料**を優先する。

新たな企業書類本文の取得、対象企業・年度・指標の拡張、継続取得、自動監視又は大量API取得は本作業の目的としない。

これらが必要と判明した場合は、必要対象・理由・取得量・期待効果を整理して停止し、Nori判断へ上げる。

### C. 本番資産

本作業では、

- 本番DB
- 正式コード
- 正式設定
- 正式API設定
- 本番運用資産
- FChart原本

を変更しない。

検証コード又は検証DBが必要な場合は隔離環境だけで扱う。

### D. トークンコスト

大量のXBRL・XML・JSON等をAIへ全文投入しない。

抽出、件数照合、重複検出、context比較、taxonomy照合等は可能な限り決定論的な機械処理を先行し、AIは例外・未知パターン・判定規則の整理へ集中させる。

## 06）合格条件・完了条件

次をすべて満たした場合に完了とする。

1. `accepted`に必要な条件が、公式根拠へ追跡可能な形で明文化されている。
2. `accepted` / `hold` / `rejected`の境界が再現可能な判定規則として整理されている。
3. 1332の中核8セルへ判定規則を適用し、全セルについて結果と理由を説明できる。
4. `accepted`となった候補がある場合、その候補について第三者が同じ入力・根拠・判定規則から同じ結果を再現できる。
5. `accepted`が0件のままの場合でも、各holdを解除できない具体的な不足根拠を特定できている。
6. 不足根拠ごとに、既存資料で解消可能か、追加公式資料確認が必要か、新規取得又は実装が必要かを区分できている。
7. 根拠のないhold解除及びacceptedへの誤混入が0件である。
8. 本番資産に変更がない。
9. 未解決事項及び次工程候補が整理されている。
10. 独立したカンによる監査が「適合（承認可）」となっている。

### 完了時の分岐

#### A. accepted生成条件が成立し、実データでもacceptedを確認

本番候補方式として次工程判断へ進む。

#### B. 判定条件は確定したが、追加公式証拠が必要

必要な追加取得対象を限定した次工程案を作成する。

#### C. 現方式では安全なaccepted生成が困難

無理に実装を継続せず、その理由と代替方式候補を提示する。

## 07）公開区分

公開可（原則公開可・禁止情報のみ除外）。

ただし、実在企業・書類の識別子、取得URL、実抽出値、実データを再現できる資料、非公開マニフェスト、隔離DB等は公開しない。

公開候補成果物は現行GitHub連携運用及び公開安全性確認に従う。

## 08）通常運用からの例外

なし。

作業途中の技術的問題又は監査指摘は、承認範囲内であればCodex側で

`調査 → 是正 → 再検証 → 独立再監査`

を反復し、「適合（承認可）」まで自走する。

ただし、新規企業書類取得、対象範囲拡大、本番資産変更、新たな権限又はNoriの方針判断が必要となった場合は停止する。
